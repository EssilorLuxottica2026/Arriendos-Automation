PROJECT CONTEXT - LEASE/RENT INVOICE AUTOMATION FOR LUCY/SAP

1. HIGH-LEVEL PURPOSE

This project automates the pre-accounting preparation work for lease/rent invoices in Colombia before the data is posted manually or automatically into Lucy/SAP.

The main business objective is:
- reduce manual effort in preparing lease/rent invoices
- standardize invoice/accounting outputs
- generate Lucy/SAP-ready files
- minimize human intervention
- avoid requiring the business user to manually add new headers or extra fields in the original source email/table

The current automation scope is aligned to the SOP:
- SOP-P2P-CO-PRO-003 Arrendamientos (Rentas) CO Rev3

The project automates logic before final posting in Lucy/SAP, including:
- information preparation and cleaning
- mapping store/vendor/CECO
- contract status checks
- rent type determination (RF vs RV)
- accounting account selection
- VAT proration
- invoice distribution/splitting rules
- generation of consolidated outputs for downstream operations

Out of scope:
- posting directly in Lucy
- posting directly in SAP
- SAP tax/withholding validation inside SAP itself
- SAP compensation steps such as F-44

The pipeline uses flexible header detection, but at minimum it expects the concepts:
- invoice_id
- vendor
- total

It can also consume if present:

- reference
- vat
- invoice_date
- due_date
- ceco
- withholding_tax
- payment_terms_text
- item_count_hint

Important code fact:
- in pipeline/processor.py, _load_invoices() only hard-requires:
  - invoice_id
  - vendor
  - total

However, for a stronger accounting result, these are highly recommended:
- invoice_date
- vat
- due_date

B. CONTROL ARRI ADMON.xlsx
- reference file
- used to map store/vendor/CECO relations

C. Contratos con condiciones.xlsx
- reference file
- used to determine contract validity, end_of_term, rent_min, status_en_rem

D. PRORATEO.xlsx
- reference file
- used to determine VAT proration percentages (vw_percent)

E. Cuadro de distribucion 2023.xls
- reference file

F. FACTURAS CONTABILIZADAS ARRIENDOS.xlsx (optional)
- historical reference

G. Macro workbook template (optional)
- used to enrich Lucy export / macro-oriented outputs

H. PDF invoice files (optional but increasingly important)
- used by pipeline/pdf_reader.py
- intended to enrich/fill missing invoice data when the invoices spreadsheet is incomplete or inconsistent


6. CORE BUSINESS LOGIC IN THE PYTHON PIPELINE

6.1 Invoice loading and standardization

The pipeline:
- normalizes incoming column names
- cleans text fields
- creates missing optional columns as None if absent
- converts dates to pandas datetime
- converts numerics (total, vat, withholding_tax, etc.)
- normalizes invoice_id
- normalizes vendor as numeric code when possible

The pipeline also computes:
- amount = total - vat

Key invoice columns after normalization:
- invoice_id
- vendor
- store
- reference
- total
- vat
- invoice_date
- due_date
- ceco
- withholding_tax
- payment_terms_text
- item_count_hint
- amount


6.2 PDF enrichment logic

If PDF invoice files are provided, pipeline/pdf_reader.py parses them and tries to extract:
- source_file
- invoice_id
- invoice_date
- due_date
- subtotal
- total
- detected_iva
- withholding_tax
- payment_terms_text
- item_count_hint
- has_zero_iva_hint
- text_excerpt
- flags

The processor then merges PDF-derived values back into invoices using normalized invoice_id matching:
- fills invoice_date if missing
- fills due_date if missing
- fills vat if missing or zero
- fills total if missing or zero
- fills withholding_tax if missing
- fills payment_terms_text if missing
- fills item_count_hint if missing
- recalculates amount using pdf_subtotal first if available

This means PDF extraction is currently an enrichment/fallback layer, not the only source of truth.


6.3 Merge with reference tables

The pipeline merges invoices with:
- CONTROL mappings
- PRORATEO mappings
- contracts data
- optional macro database

It produces:
- mapped_vendor
- mapped_store
- mapped_ceco
- mapped_ceco_key
- profit_center
- end_of_term
- rent_min
- status_en_rem
- vw_percent


6.4 Accounting/business rules

The pipeline determines:
- contract_active = whether end_of_term >= invoice_date
- rent_type = RF if contract active, otherwise RV
- account:
  - RF -> fixed account 1245150017
  - RV -> variable account 1537210004

It calculates:
- vat_total
- vat_vw
- vat_vq
- withholding_tax_amount
- invoice_total

It also builds:
- standardized accounting text
- validations report
- invoice distribution splits when needed


6.5 Distribution / split logic

The pipeline supports special distribution cases from the distribution file.

It can split one invoice into multiple target vendors/postings and proportionally distribute:
- amount
- invoice_total
- vat_total
- vat_vw
- vat_vq
- withholding_tax_amount

This is a key business rule area because some invoices do not become a single posting.

9. CURRENT PDF EXTRACTION / OCR REALITY

The project owner/user tested PDF extraction through Power Automate using AI Builder OCR.

Observed reality:
- PDFs come in many different layouts
- at least 3 provided PDFs already differ significantly
- there may be ~300 different PDF formats in total
- therefore it is not realistic to hand-map each PDF layout in Python or Power Automate

The original desire is:
- avoid requiring the human who prepares the original source table/email to add new headers manually
- avoid pushing extra manual work back to the business user
- reduce manual effort as much as possible
- find an approach that can extract fields from highly heterogeneous PDFs with high accuracy


10. POWER AUTOMATE EXPERIMENTS ALREADY DONE

Power Automate was tested as an alternative/external extraction route.

What was tried:
- manual trigger with file upload
- AI Builder OCR action: "Recognize text in an image or a PDF document"
- Excel action: "Add a row into a table"

Initial issues encountered:
- AI Builder environment/credit limitations
- incorrect mapping where the file name was accidentally sent instead of contentBytes

That was corrected.

Confirmed working pieces:
- manual trigger receives PDF content correctly
- OCR action can extract full document text
- a "Redactar" (Compose/Compose-like) action was added
- Excel insertion works

Confirmed columns successfully written by the Power Automate prototype:
- source_pdf_name
- raw_extracted_text

Example from a successful OCR run:
- source_pdf_name: "T081 ADMINISTRACION ABRIL  2026.pdf"
- raw_extracted_text: full OCR output from the PDF


11. WHY THE CURRENT POWER AUTOMATE PARSING APPROACH IS NOT THE FINAL SOLUTION

The Power Automate prototype then attempted to fill columns such as:
- invoice_id
- invoice_date
- due_date
- vendor_name or vendor
- subtotal
- invoice_total
- payment_terms

This was done using fragile text expressions like:
- split(...)
- first(...)
- trim(...)

This approach worked for one PDF layout but failed on a different PDF layout with errors like:
- array index out of bounds
- expected marker text not found

This confirms:
- OCR + hardcoded text splitting is layout-dependent
- it does not scale to ~300 heterogeneous PDF formats
- it is essentially re-implementing manual parsing logic inside Power Automate

In other words:
- it is not real multiformat document intelligence
- it is not true generalizable machine learning
- it is fragile rule-based parsing on top of OCR


12. THE REAL PROBLEM TO SOLVE

The actual problem is NOT:
- how to hardcode one PDF layout
- how to split text for one supplier

The actual problem is:

"How to reliably extract the key invoice/accounting fields from a very large and heterogeneous set of PDF invoice layouts, without requiring manual header enrichment in the original source files, and without maintaining hundreds of layout-specific parsing rules in either Python or Power Automate?"

This is the central design problem.

15. WHAT IS NOT DESIRED

The business/user does NOT want a solution that depends on:
- manually adding more headers to the original source email/table
- manually editing every invoice spreadsheet before processing
- maintaining 300 per-layout parsing rules
- moving work back to a person instead of reducing effort


16. WHAT KIND OF SOLUTION IS BEING SOUGHT

The desired solution is something closer to:
- machine learning / document intelligence / LLM-based extraction
- highly adaptable to many invoice layouts
- high-accuracy extraction of a normalized set of fields
- minimal manual maintenance
- minimal burden on business users

Potential architecture directions already under discussion include:
- AI Builder "Process documents"
- AI Builder / GPT prompt-based extraction
- OCR + LLM structured JSON extraction
- Azure Document Intelligence or similar
- using Power Automate only as an orchestrator while Python or an external service performs the intelligent extraction


17. IMPORTANT CONSTRAINTS FOR ANY PROPOSED SOLUTION

Any proposed solution should respect these constraints:

1. There may be around 300 invoice PDF formats
2. PDFs differ significantly in structure and labels
3. The original upstream source should NOT require new manual headers added by humans
4. The solution should reduce business effort, not move the burden upstream
5. The current Python pipeline should remain usable if possible
6. A normalized field schema is desirable
7. Some extracted fields may still need confidence-based human review
8. The most important system quality is maintainability at scale, not just solving one PDF
